# Pre-Mortem 1a — Brand-Uploads Studio (#180)

**Ziel:** Identifikation von Code-Praxis-Risiken (Implementierbarkeit, testbare Abhängigkeiten, stille Datenbugs) im Implementierungsplan `brand-uploads_studio_#180_1ced6ef7.plan.md`.

---

### 1. API Route OOM-Risiko (Stiller Speichercrash vor der Validierung)
- **Warum später teuer:** Der Plan kopiert für den Datei-Upload das Muster der `app/api/mpz/hotspots/icon/route.ts`. Dort wird die empfangene Datei via `const buffer = Buffer.from(await file.arrayBuffer())` direkt und vollständig in den Node.js-RAM geladen, *bevor* die eigentliche Domain-Validierung (die OOM-sicher via `readHeaderSlice` argumentiert) überhaupt greift. Lädt ein Nutzer aus Versehen eine 500-MB-Videodatei in den "Brand Upload" hoch, stürzt der Server prozessweit ab.
- **Wann es beißt:** Bei jedem manuellen Upload-Versuch einer sehr großen Datei (im Produktions- oder Staging-Betrieb). Der Next.js-API-Endpunkt reagiert mit einem `OutOfMemoryError`.
- **Billige Gegenmaßnahme jetzt:** In der `app/api/mpz/brand/upload/route.ts` **vor** dem Aufruf von `file.arrayBuffer()` zwingend die Dateigröße über das Web-API checken: `if (file.size > MAX_BRAND_BYTES) return 422`.

### 2. Cache-Busting der Vorschau-Bilder unterspezifiziert (API-Antwort fehlt `mtime`)
- **Warum später teuer:** Der Plan besagt, dass die Vorschau-Bilder in der UI mit `img src={publicPath + '?t=' + mtime}` geladen werden, um den Browser-Cache zu umgehen. Gleichzeitig orientiert sich die API-Route (`POST /api/mpz/brand/upload`) am Icon-Upload, der laut Route-Test nur `{ path, filename }` zurückgibt. Wenn das neue `mtime` nach dem Schreiben nicht in der API-Antwort mitgeliefert wird, kann das UI das Bild nicht sofort aktualisieren, ohne direkt danach noch einmal `GET /api/mpz/brand` (Manifest-Load) aufzurufen.
- **Wann es beißt:** Unmittelbar nach einem erfolgreichen Logo-Upload. Der Nutzer sieht das alte Logo, da die `POST`-Antwort keinen Timestamp liefert und React den alten `mtime`-Wert im State behält. 
- **Billige Gegenmaßnahme jetzt:** Die Funktion `ingestBrandAsset` führt ohnehin den Schreibvorgang aus. Danach direkt ein `stat` ausführen und `mtime` zurückgeben. Die Route (`POST /api/mpz/brand/upload`) nimmt dieses `mtime` mit in den 201-Response-Body auf.

### 3. Ungefangener `ENOENT`-Fehler bei optionalen Motiven (Manifest-Crash)
- **Warum später teuer:** Der Plan verlangt `listBrandManifest`, um `exists`, `byteLength` und `mtime` für jeden Slot aus dem Filesystem (`public/brand/...`) zu laden. Da laut Plan Motive "optional, noch nicht in UI verdrahtet" sind, existiert z.B. `bunting.png` zu Beginn nicht. Ein naiver `fs.promises.stat`-Aufruf auf einen fehlenden Pfad wirft einen `ENOENT`-Error und bringt die gesamte `GET /api/mpz/brand`-Route (und damit das Server-Rendering der Brand-Page) zum Absturz.
- **Wann es beißt:** Direkt beim ersten Laden der neuen `/mpz/studio/brand`-Seite, da die Dateien im Ordner `motifs/` fehlen.
- **Billige Gegenmaßnahme jetzt:** In `listBrandManifest` muss das Lesen der Datei-Metadaten zwingend durch ein `try/catch` (oder via `existsSync`) abgesichert sein, um elegant `{ exists: false, byteLength: 0, mtime: null }` zurückzugeben, wenn der Slot unbelegt ist.
