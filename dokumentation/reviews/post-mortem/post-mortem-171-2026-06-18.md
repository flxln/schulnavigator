## 4. Scope

Was im Code steht, das nicht explizit im Plan beschrieben ist:

- **`PATCH_CLIENT_ERROR_CODES` als `Set`** (`route.ts` Z. 14–23): Die Route definiert alle 422-fähigen Domain-Codes als konstantes Set und prüft damit generisch (`PATCH_CLIENT_ERROR_CODES.has(err.code) ? 422 : 500`, Z. 97). Der Plan beschreibt `mapMediumPatchError` nur funktional, nicht implementierungsseitig. Das Set ist ein sauberes Implementierungsdetail — kein Risiko.

- **`isOptionalStringClear` als benannte Hilfsfunktion** (Domain Z. 102–104): Der Plan beschreibt das Verhalten (`null`/`""` → entfernen), benennt keine spezifische Funktion. Extraktion in benannte Funktion ist sinnvoll und wartbar.

- **`quelleReadOnly`-Flag im Formular** (Form Z. 158–162): Das Formular leitet daraus ab, ob `quelle` editierbar angezeigt wird. Der Plan beschreibt das indirekt (Akzeptanzkriterium 2 + Felder-Tabelle), aber nicht als Flag. Korrekte Umsetzung.

- **`useEffect(() => { setForm(mediumToForm(medium)) }, [medium])`** (Form Z. 98–101): Formular-Reset bei Prop-Wechsel. Der Plan erwähnt das nicht, ist aber eine notwendige Robustheits-Maßnahme für den Inline-Panel-Flow.

- **`removingId`-State bleibt in `station-medien-table.tsx`** (Table Z. 72): Bereits vorhandener State — keine neue Erweiterung, nur Beibehaltung.

- **`MediumRemoveErrorCode` mit `@deprecated`-Kommentar** (Domain Z. 48–49): Plan nennt die Verbreiterung zu `MediumErrorCode`; der veraltete Alias-Typ bleibt mit JSDoc-Annotation erhalten. Sauber — vermeidet Breaking Changes an bestehenden Importern ohne sofortige Migration zu erzwingen.

Keine tangentialen Änderungen, stille Refactors in anderen Dateien oder Felder, die nicht dem Plan entsprechen.
