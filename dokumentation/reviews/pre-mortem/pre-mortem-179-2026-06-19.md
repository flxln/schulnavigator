### Fund 1 — `EXPECTED_STATION_COUNT` und `HUB_SLUG_MAP` als Modul-Top-Level-Konstanten in `validate-stations.ts`

```ts
// validate-stations.ts Z. 29, 49
import { buildHubStations, HUB_SLUG_MAP } from '@/lib/schoolhouse-hub-map'
const EXPECTED_STATION_COUNT = Object.keys(HUB_SLUG_MAP).length  // ← statisch beim Import
```

Der Plan sieht vor, `validateStation` (Z. 724: `raw.slug in HUB_SLUG_MAP`) und `validateStationsFile`
(Z. 895: `Object.keys(HUB_SLUG_MAP)`) auf `getHubSlugMap()` umzustellen, indem
`ValidateStationsFileOptions` ein optionales `hubSlugMap?`-Feld bekommt.

**Das Versäumnis:** `EXPECTED_STATION_COUNT` ist eine **Modul-Top-Level-Konstante**, die beim ersten
Import von `validate-stations.ts` eingefroren wird — egal ob später `hubSlugMap?` übergeben wird oder
nicht. Die interne Funktion `validateStation` erhält aktuell keinen eigenen `hubSlugMap`-Parameter;
der Refactor müsste ihn durch die Aufrufkette bis dort hinunter durchschleifen (`validateStationsFile`
→ `validateStation`). Das ist in der Aufgabenbeschreibung (Todo `consumers-refactor`) nicht explizit
als Signatur-Änderung von `validateStation` aufgeführt.

- **Warum später teuer:** Wird nur `ValidateStationsFileOptions.hubSlugMap` hinzugefügt, aber die
  interne `validateStation`-Signatur nicht angefasst, kompiliert der Code — aber der Check
  `raw.slug in HUB_SLUG_MAP` (Z. 724) prüft weiterhin die statische Konstante, nicht die per Post-Write
  übergebene neue Map. Der Cross-Check würde still die alte Map nutzen und keinen Fehler werfen, auch
  wenn ein temporär ungültiger Slug übergeben wurde.
- **Wann es beißt:** Test in `mpz-hub-config.test.ts`, der einen neuen `hubSlugMap`-Inhalt per
  `createMpzContentIo({ … })` injiziert und erwartet, dass `validateStation` diesen respektiert —
  schlägt nicht fehl (falsches Grün), weil die interne Prüfung stale ist.
- **Billige Gegenmaßnahme jetzt:** Im Plan explizit festhalten, dass `validateStation` einen dritten
  Parameter `hubSlugMap: Record<string, HubSlugMapping>` erhält und `EXPECTED_STATION_COUNT` auf
  `Object.keys(hubSlugMap).length` umgerechnet wird — als lokale Variable, nicht Modul-Konstante.
  Alternativ: `EXPECTED_STATION_COUNT` aus `getHubSlugMap()` lazy berechnen.

### Fund 2 — Dreifach-Rollback ohne atomaren Koordinationspunkt

Der Plan beschreibt: „Rollback aller drei Dateien → 422 `VALIDATION`" (AC 8) und „je Datei `.bak`,
atomarer Rename via `writeAtomicFile`, ein `withMpzWriteLock`-Block" (AC 7).

Das bestehende `writeAtomicFile` ist **single-file**: schreibt eine tmp-Datei und renamt sie. Für
drei Dateien (`hub-slug-map.json`, `station-accents.json`, `station-icons.json`) braucht
`writeHubConfig` eine Sequenz:

```
write tmp-A → write tmp-B → write tmp-C
→ validate
→ rename A / rename B / rename C   ←── was passiert, wenn rename B oder C crasht?
→ bei Fehler: restore .bak-A, .bak-B, .bak-C
```

Das aktuelle `commitEmbedAllowlistWrite` kennt nur eine Datei und löscht bei Fehler die *eine* tmp.
Ein dreifacher Rename ist **nicht atomar** — nach erfolgreichem rename A und gescheitertem rename B
liegt die Disk in einem halbkonsistenten Zustand, und die `.bak`-Restore-Logik ist nicht im Plan
spezifiziert.

- **Warum später teuer:** Halbkonsistenter Zustand (z. B. neue `hub-slug-map.json`, aber alte
  `station-accents.json`) bricht beim nächsten `getHubSlugMap()`-Aufruf keine Exception aus — stille
  Datendrift über Neustart hinaus.
- **Wann es beißt:** Wenn beim Schreiben (z. B. wegen voller Disk oder Race auf dem Dateisystem) der
  dritte rename fehlschlägt. In der Entwicklung kaum reproduzierbar, im Produktions-Deploy auf
  beschränkter Disk (z. B. Vercel serverless /tmp) real.
- **Billige Gegenmaßnahme jetzt:** Plan um ein konkretes Rollback-Protokoll für `writeHubConfig`
  erweitern: alle drei tmp-Dateien schreiben → Inline-Validator → alle drei renamen → bei *jedem*
  Rename-Fehler: verbleibende tmps löschen + alle drei `.bak`s restoren. Das ist ~15 Zeilen mehr als
  das Embed-Muster, aber explizit dokumentiert verhindert es Implementierungs-Spekulation.

### Fund 3 — `buildHubStations` ruft intern `accentForSlug → GS39_STATION_ACCENT_HEX` direkt auf

```ts
// schoolhouse-hub-map.ts Z. 112–116
function accentForSlug(slug: string): string {
  const hex = GS39_STATION_ACCENT_HEX[slug]   // ← statischer Import
  …
}
// Z. 176
...buildVisuals(accentForSlug(station.slug)),
```

Der Plan sieht vor, `buildHubStations` einen optionalen `accents`-Parameter für den Post-Write-
Cross-Check zu bekommen (`buildHubStations(stations, { hubSlugMap, accents })`). Das steht in der
Pre-Mortem-Prophylaxe-Tabelle (Plan Z. 281).

**Das Versäumnis:** Der Plan spezifiziert nicht, wie `accentForSlug` intern umgestellt wird. Wenn
nur der äußere Parameter `accents?` hinzugefügt wird, aber die interne `accentForSlug`-Funktion
`GS39_STATION_ACCENT_HEX` direkt nutzt, dann ignoriert `buildHubStations` im Post-Write-Pfad die
frisch geschriebenen Akzente und prüft stattdessen die statische Codekonstante — eine stille Nicht-
Validierung.

- **Warum später teuer:** `buildHubStations` als Cross-Check-Aufruf liefert `ok`, obwohl ein neuer
  Hex-Wert aus `station-accents.json` invalid wäre (z. B. `#XYZ123`) — der Test in
  `mpz-hub-config.test.ts` würde fälschlicherweise grün bleiben.
- **Wann es beißt:** Im Unit-Test, wenn ein falscher Akzentwert als `accents`-Option übergeben wird
  und erwartet wird, dass `buildHubStations` ihn ablehnt — wird er nicht, weil `accentForSlug` ihn
  ignoriert. Bemerkt man erst beim manuellen Speichern eines absichtlich fehlerhaften Hex-Wertes.
- **Billige Gegenmaßnahme jetzt:** Im Plan festhalten: `accentForSlug` bekommt einen zweiten
  Parameter `accentsOverride?: Record<string, string>` (oder wird zu einer Closure innerhalb von
  `buildHubStations` umgebaut). Der `options.accents`-Wert wird an `accentForSlug` durchgereicht.
  Alternativ: Der Cross-Check-Aufruf nach dem Write validiert Akzente nur über den separaten
  Inline-Validator `validateStationAccentsContent`, nicht über `buildHubStations` — dann muss
  `buildHubStations` nicht umgebaut werden.

## Was solide ist

**IO-Fehlerbehandlung:** Das Muster `writeAtomicFile` + `MpzContentIoError` ist aus #178 bewährt.
Die Backup-Logik (`copyFile` vor Write) ist klar. Für den Single-File-Fall gibt es nichts zu
beanstanden.

**Lucide-Registry-Trennung:** JSON speichert nur den Namen, Registry bleibt Code — kein
Serialisierungs-Problem mit React-Komponenten. Der Plan ist hier durchdacht.

**Cache-Reset für Tests:** `resetHubConfigCacheForTests()` analog zu #178 ist explizit genannt —
dieser Fehler aus früheren Issues wird nicht wiederholt.

**`listAssignableSlotIds`:** Filterung von `kind === 'deko'` direkt aus `HUB_SLOTS` (bleibt Code) —
kein stale-Import-Problem, da `HUB_SLOTS` nie aus JSON geladen wird.
