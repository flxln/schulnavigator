# Pre-Mortem 1a — Code-Praxis: MPZ UI Datei ersetzen (#188)

Die Analyse fokussiert sich auf Implementierungsdetails und Fallstricke, die beim Schreiben der `StationMediumEditForm` auftreten werden.

### TypeScript-Kompilierungsfehler bei Zugriff auf `UPLOAD_RULES`
- **Warum später teuer:** Der Build (`npm run build`) wird abbrechen. `medium.typ` hat im Formular programmatisch den breiteren Typ `MediumTyp` (beinhaltet `link` und `embed`). Auch wenn `canReplaceMediumFile` logisch sicherstellt, dass es sich um einen Upload-Typ handelt, weiß TypeScript das nicht. Der direkte Index-Zugriff `UPLOAD_RULES[medium.typ]` für `accept` und `maxBytes` führt zu einem Type-Error ("implicitly has any type").
- **Wann es beißt:** Sofort in der IDE oder beim ersten Build, wenn die UI-Attribute dynamisch aus dem Regelwerk ausgelesen werden.
- **Billige Gegenmaßnahme jetzt:** Nutze die existierende Type-Guard-Funktion `isUploadTyp(medium.typ)` aus `mpz-upload-rules.ts` für den sicheren Zugriff, oder implementiere `canReplaceMediumFile` explizit als Type-Guard (`medium is Medium & { typ: UploadTyp }`).

### Stille Dateninkonsistenz: React State vs. Unmount des File-Inputs
- **Warum später teuer:** Wenn die Umsetzung einen React-State `selectedFile` nutzt, entsteht ein Bug, wenn das DOM-Element versteckt wird: Wechselt der Nutzer bei einem Video die `videoSource` auf "youtube", verschwindet der Replace-Block. Wechselt er zurück, rendert das `<input type="file">` neu als "Keine Datei ausgewählt". Der `selectedFile`-State hält aber noch unsichtbar die alte Datei. Ein Klick auf "Ersetzen" lädt diese unerwartet hoch.
- **Wann es beißt:** Bei Video-Medien, wenn ein Redakteur im Formular mit dem Dropdown `videoSource` experimentiert.
- **Billige Gegenmaßnahme jetzt:** Den State `selectedFile` in einem `useEffect` auf `null` zurücksetzen, wenn sich `canReplaceMediumFile` auf `false` ändert (oder den Input strikt uncontrolled über eine Ref auslesen).

### Fehlende clientseitige Dateigrößen-Prüfung blockiert Uploads
- **Warum später teuer:** Videodateien dürfen laut `UPLOAD_RULES` bis zu 150 MB groß sein. Ohne clientseitige Prüfung blockiert der Browser beim Versuch, ein z.B. 1 GB großes Rohvideo über `fetch` hochzuladen. Das verschwendet Bandbreite und Zeit des Redakteurs, nur um am Ende serverseitig (Next.js Body-Limit oder API-Fehler 413/422) abgewiesen zu werden.
- **Wann es beißt:** Wenn ein Nutzer versehentlich eine viel zu große Datei (z.B. unkomprimiertes Video) auswählt und auf "Ersetzen" klickt.
- **Billige Gegenmaßnahme jetzt:** Vor dem `fetch`-Call in `handleFileReplace` eine synchrone Abfrage einbauen: `if (selectedFile.size > UPLOAD_RULES[uploadTyp].maxBytes) { setError('Datei zu groß'); return; }`.
