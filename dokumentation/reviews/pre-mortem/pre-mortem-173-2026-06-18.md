## Bewertung: Was solide ist

**Fehlerbehandlung (Domain + Route):** Das Dreier-Muster `MpzUploadError('VALIDATION'|'COLLISION'|'IO')` plus `MpzContentIoError` ist konsequent aus den Referenz-Ingests übernommen. Die Fehlertabellen im Plan sind vollständig und konsistent mit `mpz-upload-rules.ts` Z. 21–30. Kein offensichtlicher Gap.

**IO-Abgrenzung:** Vollbuffer aus `file.arrayBuffer()` im Route-Handler — dann nur noch `IngestSource = { buffer }` in die Domain. Das hält die Domain frei von `fs`-Direktzugriffen. Genau dasselbe Pattern wie `mpz-medium-ingest.ts` Z. 35 / `mpz-hotspot-icon-ingest.ts`.

**Rollback beim Formatwechsel 360°:** Das Löschen der alten Datei nach erfolgreichem JSON-Write (Schritt 8 im Plan) ist analog zum WAV-Rollback in `mpz-dialog-audio-ingest.ts` Z. 316–323 — die Reihenfolge (erst schreiben, erst dann alten Pfad löschen) ist korrekt.

## Befunde

### Befund 1 — `image-dimensions.ts` braucht `fileTypeFromBuffer` für WebP, aber der Plan fordert den vollen Buffer

Der Plan sieht `readImageDimensions(buffer)` aus dem vollen Upload-Buffer vor und nennt für WebP den „RIFF-Header in den ersten ~32 Bytes". Das RIFF-`VP8 `- oder `VP8L`-Chunk liegt tatsächlich in den ersten 12 Bytes — kein Problem.

**Kritischer Teil:** Für JPEG braucht `jpegDimensions` (identische Implementierung wie `validate-station-assets.ts` Z. 46–62) den **kompletten** Buffer, um den `SOF0`-/`SOF2`-Marker zu finden. Dieser Marker sitzt je nach JPEG-Encoder nach Thumbnail-Exif-Block, ICC-Profil, etc. weit hinter den ersten 4 096 Bytes. Der Plan nennt explizit „Dimensionen aus vollem Buffer" — allerdings wird `readHeaderSlice` (aus `mpz-medium-ingest.ts` Z. 65–85) nur einen 4 096-Byte-Slice liefern, wenn der Aufrufer die vorhandene Utility benutzt.

Die neue `image-dimensions.ts` erhält den Buffer aus `file.arrayBuffer()` im Route-Handler — dort steht der volle Buffer bereit. **Aber:** Wenn `validateRaumbildUpload` den gleichen `readHeaderSlice`-Mechanismus nutzt wie die anderen Ingest-Libs, dann hat sie nur den Slice. Der Plan erwähnt diesen Unterschied nicht: Soll `validateRaumbildUpload` den vollen Buffer oder einen Slice entgegennehmen?

- **Warum später teuer:** Produziert bei JPEG mit großem Exif-Block (`null` aus dem Parser) → `VALIDATION`-Fehler „Dimensionen nicht lesbar", obwohl die Datei gültig ist. Tritt in CI nicht auf (Minimal-Fixtures ohne Exif), aber beim ersten echten Upload einer iPhone-Kamera-JPEG.
- **Wann es beißt:** Erster realer Raumbild-Upload von einer Kamera (iOS/Android) mit Exif-Daten. Test-Fixture „2500×1000 px JPEG" ohne Exif beißt nicht.
- **Billige Gegenmaßnahme jetzt:** Im Plan explizit festhalten: `validateRaumbildUpload` nimmt `fullBuffer: Buffer` (nicht `headerSlice`), und `image-dimensions.ts` operiert immer auf dem vollen Buffer. Der Route-Handler übergibt `Buffer.from(await file.arrayBuffer())` direkt — kein separates `readHeaderSlice` für die Dimensions-Funktion.

### Befund 2 — Formatwechsel 360°: kein Kompensations-Rollback wenn `writeStations` scheitert

Der Plan beschreibt Schritt 7 (Datei schreiben) und Schritt 8 (alte Datei löschen) als sequenziell nach dem JSON-Write. Das Dialog-Audio-Ingest-Pattern zeigt aber die korrekte Reihenfolge klar:

1. Datei schreiben (mit `.bak`)  
2. JSON schreiben  
3. **Bei JSON-Fehler: `rollbackWav` → Datei aus `.bak` zurückstellen** (Z. 316–318 in `mpz-dialog-audio-ingest.ts`)  
4. Nur bei Erfolg: `.bak` löschen + alte Datei entfernen

Im Raumbild-Plan fehlt dieser Rollback für den Formatwechsel-Fall explizit. Wenn `writeStations` nach dem `writeFileWithReplace` wirft (z. B. `postValidate`-Fehler wegen ungültigem Ratio einer anderen Station), liegt die neue Datei auf Disk — aber `stations.json` zeigt noch den alten Pfad. Zusätzlich wurde die alte Datei möglicherweise noch nicht gelöscht, da das Löschen nach dem JSON-Write geschehen soll — das ist zufällig korrekt. Aber wenn `writeStations` wirft, ist der Disk-State inkonsistent (neue Datei da, JSON alt).

- **Warum später teuer:** Stille Datei-Inkonsistenz — nach einem `postValidate`-Fehler liegt die neue `.webp`-Datei unter `360/{slug}.webp`, aber `stations.json` zeigt `panorama360: /stations/360/{slug}.jpg`. Nächste Validierung meldet dann eine fehlende Datei.
- **Wann es beißt:** `writeStations({ postValidate: true })` schlägt fehl, weil eine andere Station kurz zuvor einen Asset-Fehler hatte. Oder: Race-Condition mit parallelem Write unter Write-Lock ist ausgeschlossen — aber `postValidate` selbst kann scheitern.
- **Billige Gegenmaßnahme jetzt:** Im Plan den Ablauf im Ingest explizit mit Try-Catch spezifizieren: Bei `writeStations`-Fehler → `safeUnlink(newDestPath)`. Das ist eine 3-Zeilen-Addition im Implementierungs-Abschnitt, kein Design-Change.

---

### Befund 3 — `validate-station-assets.ts` prüft 360°-Ratio nur für JPEG, WebP läuft durch `checkPath` ohne Ratio-Check

Der Plan nennt `validate-station-assets.ts` Z. 64–87 als Ausgangslage. Im Code (Z. 177–191) gilt:

```typescript
if (/\.jpe?g$/i.test(fsPath)) {
  checkPanorama360Asset(…) // JPEG: Ratio-Check ✓
} else {
  checkPath(…)             // WebP: nur Existenz + Größe, kein Ratio
}
```

Nach dem Upload eines 360°-WebP schreibt der Ingest den korrekten Pfad in `stations.json`. Der Build-Validator prüft danach das Ratio **nicht** für WebP. Die neue API garantiert das korrekte 2:1-Ratio (harte Validierung in der Domain) — aber der nachgelagerte Build-Validator und `postValidate` decken eine defekte WebP-Datei (z. B. manuell abgelegt oder durch einen Bug erzeugt) nicht auf.

Der Plan markiert die Anpassung von `validate-station-assets.ts` als „MODIFY (optional)" — das ist korrekt. Aber der Zusammenhang zum WebP-Ratio-Gap steht dort nicht. Wenn jemand das optionale DRY-Refactoring macht und `image-dimensions.ts` einbindet, wäre der Ratio-Check für WebP trivial. Wenn nicht, bleibt der Gap.

- **Warum später teuer:** Ein defektes WebP (2000×1200 statt 2000×1000) übersteht Build-Validator und `postValidate`, ist im Studio nicht sichtbar, und zeigt im 360°-Viewer einen verzerrten Raum — nur schwer debuggbar.
- **Wann es beißt:** Sobald das erste 360°-WebP manuell (ohne Studio) unter `/stations/360/` abgelegt wird. Die Upload-Route schützt, aber der manuelle Ablege-Weg bleibt ungeprüft.
- **Billige Gegenmaßnahme jetzt:** In der offenen Frage #1 des Plans (Build-Validator angleichen) explizit notieren: das MODIFY schließt auch den WebP-Ratio-Check ein. Optional bleibt es, aber der Grund ist nun dokumentiert. Alternativ: `checkPanorama360Asset` um einen WebP-Branch erweitern — 10 Zeilen, wenn `image-dimensions.ts` bereits existiert.
