## Funde

### 1. `addStationHotspot` — `NO_MEDIAS`-Guard blockiert Dialog vor dem Dialog-Check — stille Ablehnung am ersten Testtag

```
// mpz-station-hotspots.ts:311–316
if (!station.medien?.length) {
  throw new MpzStationHotspotsError(
    'NO_MEDIAS',
    `Station "${slug}" hat keine Medien — zuerst Medium ingestieren.`,
  )
}
```

- **Warum später teuer:** Der Guard steht *vor* jeder Unterscheidung nach `action`. Eine Station, die ausschließlich Dialog-Hotspots verwenden soll (kein Medium nötig), bekommt sofort `400 NO_MEDIAS`. Der erste Unit-Test für `addStationHotspot` mit `action: "dialog"` und leerer `medien`-Liste schlägt fehl — nicht weil die Domain falsch implementiert ist, sondern weil der Pfad gar nicht erreicht wird.
- **Wann es beißt:** Tag 1, Unit-Test `addStationHotspot – dialog, keine Medien → 200`. Außerdem in der UI: Stationen wie `daz` oder `pc-raum`, die laut Plan als Referenz-Regression dienen, haben Medien — der Fehler bleibt in der Happy-Path-Regression unsichtbar, wird aber von einer Station ohne Medien sofort ausgelöst.
- **Billige Gegenmaßnahme jetzt:** Den Guard an `action` konditionieren, bevor er geworfen wird:

  ```ts
  // Vor validateHotspotId einfügen:
  const isDialog = (input as { action?: string }).action === 'dialog'

  if (!isDialog && !station.medien?.length) {
    throw new MpzStationHotspotsError('NO_MEDIAS', …)
  }
  ```

  Das erfordert, dass `AddStationHotspotInput` einen optionalen `action`-Discriminator bekommt — was der Plan sowieso vorsieht. Reihenfolge im Plan: korrekt (Domain zuerst), aber der Guard muss explizit als erster Schritt in Schritt 4 der POST-Sequenz abgehandelt werden.

### 2. `buildMergedHotspotInput` / `patchStationHotspot` — Dialog-PATCH legt `mediumId: undefined` ins Merge-Objekt und erzeugt stille Dateninkonsistenz

```
// mpz-station-hotspots.ts:162–168
const merged: AddStationHotspotInput = {
  id: existing.id,
  mediumId: 'mediumId' in patch ? patch.mediumId! : existing.mediumId!,
  label: …,
  icon: …,
  iconSize: …,
}
```

- **Warum später teuer:** `AddStationHotspotInput` hat `mediumId: string` als Pflichtfeld (Zeile 41). Ein Dialog-Hotspot in `stations.json` hat kein `mediumId`. `existing.mediumId` ist also `undefined`, `patch.mediumId` ebenso. Das ergibt `merged.mediumId = undefined!` — TypeScript schweigt wegen des `!`-Operators. `buildFlatDialogHotspot` (neuer Builder) muss dieses Objekt akzeptieren, ohne `mediumId` zu schreiben. Wenn stattdessen versehentlich der bestehende `buildFlatHotspot` aufgerufen wird (z. B. weil der Verzweigungs-If vergessen wurde), schreibt er `mediumId: undefined` ins JSON — der Validator schlägt danach mit `VALIDATION 422` fehl, aber der Fehler ist schwer zu debuggen.
- **Wann es beißt:** Erster PATCH-Test für Dialog-Hotspot + falscher Builder → `postValidate` wirft `422`. Alternativ: lautloser `undefined` im JSON wenn `postValidate` die Regel noch nicht kennt.
- **Billige Gegenmaßnahme jetzt:** `AddStationHotspotInput` in eine Discriminated Union umbauen *oder* eine separate `AddStationDialogHotspotInput` definieren (Plan erwähnt das). Dann gibt es für Dialog-PATCH eine eigene `buildMergedDialogHotspotInput`-Funktion — im Plan Schritt 5 bereits vorgesehen. Wichtig: den Builder-Dispatch in `patchStationHotspot` explizit an `existing.action === 'dialog'` koppeln, **nicht** nur an `viewer`, damit der falsche Builder nicht aus Versehen greift.

### 3. `parsePatch` — Dialog-Felder (`mascot`, `mascotSize`, `mascotFlipX`, `bubblePitchOffset`) sind nicht deklariert — Route gibt `400 INVALID_BODY` für valide Dialog-Patches

```
// [hotspotId]/route.ts:72–74
if (Object.keys(patch).length === 0) {
  return null
}
return patch
```

`parsePatch` akzeptiert nur: `label`, `mediumId`, `x`, `y`, `yaw`, `pitch`, `icon`, `iconSize`. Ein PATCH-Body `{ mascot: "dino" }` ergibt nach dem aktuellen Code `patch = {}` → `return null` → Route antwortet `400 INVALID_BODY` mit der Meldung „Body muss mindestens ein gültiges Feld … enthalten." Das ist der **erste Compilerfehler-äquivalente Laufzeitblock** — keine Domain-Logik wird erreicht.

- **Warum später teuer:** Die Route-Tests für Dialog-PATCH schlagen am ersten Tag fehl, obwohl Domain und Builder korrekt sind. Außerdem muss die Fehlermeldung in Zeile 107 aktualisiert werden (sie listet die erlaubten Felder auf — Dialog-Felder fehlen).
- **Wann es beißt:** Erster `PATCH`-Routentest mit `body = { mascot: "dino" }` → `400`, erwartet `200`.
- **Billige Gegenmaßnahme jetzt:** `parsePatch` um die Dialog-Felder erweitern (Plan Schritt 2 — `parsePatch()` um Dialog-Felder). Die Typ-Guards für `mascot` (string), `mascotSize` (nullable number), `mascotFlipX` (nullable boolean), `bubblePitchOffset` (nullable number) analog zu den bestehenden Feldern schreiben. Fehlermeldung in Zeile 107 ergänzen.

## Solide Bereiche (hingeschaut, kein Fund)

**Fehlerbehandlung POST-Route (`route.ts:38–52`):** Mapping-Logik ist korrekt aufgebaut. Neue Codes landen sauber als `400`, wenn sie in `CLIENT_ERROR_CODES` eingetragen werden — das ist der einzige notwendige Schritt. Kein struktureller Umbau nötig.

**`mergeBuiltHotspot` / `REBUILT_HOTSPOT_KEYS`:** Die Erweiterung um `mascot`, `mascotSize`, `mascotFlipX`, `bubblePitchOffset` ist mechanisch und risikoarm — das Array-`delete`-Pattern ist robust.

**`isMediaHotspot` in `station-hotspots-table.tsx:41`:** Bereits korrekt als `hs.action !== 'dialog'` implementiert (nicht `hs.action === 'medium'`). `canEdit = isMediaHotspot(hs)` (Zeile 123) muss auf `true` für alle gesetzt werden — aber der Check ist strukturell bereits vorbereitet. Kein versteckter Logikfehler.

**Konstanten (`constants.ts:3–6`):** `MIN_MASCOT_SIZE_NORM`, `MAX_MASCOT_SIZE_NORM`, `DEFAULT_MASCOT_SIZE_NORM` sind exportiert und korrekt. Die Add-Form kann sie direkt importieren.
