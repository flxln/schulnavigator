### Die 4 scharfen Funde (Preview)

1. **Card-Radius-Token 8px vs. Code-Realität 12px** — Spec und Plan fordern 8px (`--mpz-r-card: var(--s-2)`), aber ~25 Consumer nutzen `rounded-gs39-md` (= `--r-md` = **12px**). Der Token wird in #206 definiert, aber mangels Consumer-Migration von niemandem genutzt. Erst #207+ migriert — und dann ändert sich der Radius von 12px auf 8px für alle Cards. Das ist ein **versteckter visueller Breaking Change**, der als "Foundation only" deklariert wird.

2. **Nav-Active-Stripe: Spec sagt Grün, Code macht Weiß, Plan schweigt zur Farbe** — DESIGN.md Z. 161: "Brand Green left-border stripe (4px)". Code (`studio-shell.tsx` Z. 423): `border-white`. Plan definiert `--mpz-nav-active-stripe: 4px` (Breite), aber die **Farbe fehlt im Token-Mapping**. Wenn #207 die Shell migriert, ist unklar: `border-accent` (Grün) oder `border-white`?

3. **Validation Card: unvollständige Diskriminierung** — DESIGN.md Z. 157 lässt offen: "green left-accent **OR** light green tint". Der Plan (Z. 43) sagt "grüner Akzent links". Die Abnahme-Checkliste (Z. 196) fordert `accent/border-accent`. Drei Quellen, zwei Interpretationen — der Consumer-Vertrag für `MpzCard variant="validation"` ist nicht eindeutig.

4. **Sidebar-Breite 240px vs. Code 256px** — Spec: 240px. Code: `lg:w-64` (256px). Plan definiert Token 240px, aber die Shell nutzt Tailwind-Klassen, nicht den Token. #207 müsste beides ändern — oder der Token bleibt eine tote Variable.
