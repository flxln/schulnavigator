**Reviewer:** Antigravity (Senior-Engineer-Blick)

## Fund 1: `writeCoachMessages(postValidate)` — falsches postValidate-Modell

### Das ist kein `runNpmScript`-Modell — das ist ein TypeScript-Modell

**Was der Plan sagt:**  
Plan Z. 59: „Nach jedem Write `npm run validate:coach` via `runNpmScript`" — analog `writeStations({ postValidate: true })`.

**Was der Code tut:**  
`writeStations({ postValidate: true })` ruft _kein_ `runNpmScript`. Es ruft `commitStationsWrite()` (Z. 129–171 in `mpz-content-io.ts`), das `validateStationsContent()` aufruft — reines TypeScript, kein Subprocess.

Der Plan zitiert `runNpmScript` aus `mpz-deploy-runner.ts` als Mechanismus. Das ist der _Deploy-Runner_ für lang laufende Build-/Rotate-Skripte (60 s Timeout, 32 MB maxBuffer). Er existiert nur dort.

**Zwei Implementierungspfade, die der Plan nicht festlegt:**

| Pfad A | Pfad B |
|--------|--------|
| Eigener TS-Inline-Validator analog `validateStationsContent` | Subprocess `npm run validate:coach` via `runNpmScript` |
| Schnell, unit-testbar, kein npm im PATH nötig | Näher am Validator-SSOT, aber: Subprocess in API-Route, 60 s Timeout, Datei muss bereits auf Disk liegen |

**Warum später teuer:**  
Wählt man Pfad B (Subprocess), muss `coach-messages.json` _vor_ dem Script-Aufruf auf Disk geschrieben sein — Rollback aus `.bak` ist dann destruktiv-async. Wählt man Pfad A, ist ein Drift zwischen TS-Domain und `.mjs`-Validator möglich (Stationszahl-Check fehlt in Domain, da `readStations()` im Domain-Lock nicht aufgerufen wird).

**Wann es beißt:**  
- Pfad B: Jeder `writeCoachMessages`-Test braucht echten npm-Aufruf oder `vi.mock('node:child_process')` — erheblicher Mock-Aufwand in CI.  
- Pfad A: Domain prüft `milestone < stationCount` nicht (stationCount ist Disk-Information); postValidate mit Script fängt es ab — aber nur wenn Script-Aufruf _nach_ atomarem Write + _vor_ Response kommt. Timing/Rollback-Pfad ist unklar.

**Billige Gegenmaßnahme jetzt:**  
Im Plan explizit festlegen: **Pfad B mit tmp-Datei-Strategie** (Write in `coach-messages.json.tmp`, Script validiert tmp, rename bei Erfolg, unlink bei Fehler) — oder **Pfad A mit explizitem `stationCount`-Parameter** den die Domain aus `readCoachMessages`-Lock-Schritt übernimmt. Nicht beides halb.

## Fund 2: `writeAtomic` in `mpz-content-io.ts` — hardcodierter `stations.json`-Dateiname im tmp-Pfad

### Der Plan erbt eine versteckte Kopplung beim atomaren Write

**Was der Code tut:**  
`writeAtomic()` (Z. 108–127) baut den tmp-Pfad so:

```typescript
const tmpPath = join(dir, `stations.json.${process.pid}.tmp`)
```

Der tmp-Name ist **hardcodiert** auf `stations.json`. Gleiches gilt für `commitStationsWrite()` (Z. 136).

**Was der Plan erfordert:**  
`writeCoachMessages` soll die gleiche atomare Write-Logik nutzen (Plan Z. 58: „atomarer Rename"). Wenn er `writeAtomic` direkt übernimmt, entsteht bei parallelem stations-Write + coach-Write eine Kollision: beide legen `stations.json.<pid>.tmp` im gleichen Verzeichnis `data/` an — `coach-messages.json` liegt in `content/`, `stations.json` in `data/`, also _kein_ Kollisionsproblem. **Aber:** Wenn der Implementierende die Funktion blind kopiert und vergisst, den Dateinamen anzupassen, entsteht ein tmp mit dem falschen Namen — kein Fehler, aber irreführendes Debugging bei Cleanup-Fehlern.

**Wann es beißt:**  
Erst beim ersten parallelen Write-Fehler, der die tmp-Datei nicht aufräumt — dann liegt `stations.json.<pid>.tmp` im `content/`-Verzeichnis und verwirrt den nächsten Entwickler.

**Billige Gegenmaßnahme jetzt:**  
`writeAtomic` zu einer parametrisierten Hilfsfunktion `writeAtomicFile(targetPath, content)` extrahieren, bei der der tmp-Name aus `targetPath` abgeleitet wird (`${basename(targetPath)}.${process.pid}.tmp`). Coach-IO nutzt dann dieselbe Funktion — korrekt für beide Dateien.

## Fund 3: `LAST_HUB_COMPLETE`-Schutz ist in DELETE blockierend — aber DELETE-Route erhält keinen Stationscontext

### Der Validator prüft `hubCompleteCount !== 1` global; Domain-DELETE muss das pre-write checken

**Was der Plan sagt:**  
Plan Z. 182: `LAST_HUB_COMPLETE` — DELETE der _einzigen_ `hub-complete`-Message → 400.

**Was das bedeutet in Code:**  
In `removeCoachMessage` muss nach dem Entfernen (oder davor) geprüft werden, ob noch genau eine `hub-complete` übrig bleibt. Das ist eine Zählabfrage über das gesamte `messages[]`-Array — sauber implementierbar.

**Die Lücke:**  
Der Validator (Z. 128–130) prüft `hubCompleteCount !== 1` — d. h. er verbietet auch `hubCompleteCount === 0` _und_ `hubCompleteCount > 1`. Der Plan erlaubt `DUPLICATE_HUB_COMPLETE` für POST/PATCH (Z. 181). Das ist konsistent. **Aber:** Die Domain-Funktion `removeCoachMessage` muss _vor_ dem Write prüfen, ob die zu löschende Message die letzte `hub-complete` ist. Das bedeutet: sie liest die aktuelle Liste, zählt `hub-complete`-Einträge, wirft `LAST_HUB_COMPLETE` wenn Count === 1 und die zu löschende Message `hub-complete` ist.

Der `withMpzWriteLock`-Block liest die Datei, mutiert, prüft — das ist korrekt. **Aber der Plan nennt keinen `CoachWriteResult`-Rückgabetyp** für die Domain-Funktionen. `mpz-station-dialog.ts` gibt `DialogWriteResult` zurück (station + mtime). `removeCoachMessage` muss eine analoge Struktur zurückgeben — vermutlich `{ messages: CoachMessage[], mtime: string | null }`. Das fehlt im Plan komplett.

**Warum später teuer:**  
Die Route (`DELETE /api/mpz/coach/messages/[messageId]`) braucht die neue Message-Liste, um einen sinnvollen Response-Body zu senden (oder zumindest `mtime` für `markMpzStudioDirty()` + `validateNow()`). Ohne explizit definierten Return-Type werden Route und Domain-Funktion separat entwickelt und koppeln sich erst beim Integrationstest.

**Wann es beißt:**  
Route-Test schlägt fehl oder gibt `undefined` zurück, weil Domain `void` oder `CoachMessagesFile` zurückgibt, Route aber `{ mtime }` erwartet.

**Billige Gegenmaßnahme jetzt:**  
Jetzt im Plan einen `CoachWriteResult = { messages: readonly CoachMessage[]; mtime: string | null }` festlegen, den alle drei Domain-Funktionen zurückgeben. Analog `DialogWriteResult`.

---

## Positiv-Befund: Fehlerbehandlung und Guard-Anbindung sind solide

Der Plan spiegelt `DIALOG_CLIENT_ERROR_CODES`-Pattern korrekt als `COACH_CLIENT_ERROR_CODES`-Set (Plan Z. 149). `assertMpzStudioAccess` aus `mpz-studio-guard.ts` (Z. 32–40) ist bereits der etablierte Guard — kein neuer Guard-Code, kein Risiko. `withMpzWriteLock` für Coach schützt sauber gegen parallele Hub- und Coach-Writes auf derselben Queue, da der Lock globalen State in `mpz-content-io.ts` hält (Z. 300) und Coach-Writes einreihen können — solange sie `withMpzWriteLock` aus derselben Datei importieren.

IO-Fehlerklasse `MpzContentIoError` mit `VALIDATION`/`IO` ist ausreichend für das 422/500-Mapping.

|---|--------------|------------------------------|

| 2 | **`writeAtomic`-Generalisierung:** Jetzt extrahieren oder in `writeCoachMessages` copy-pasten? | Irreführendes Debugging bei tmp-Kollisionen; technische Schuld für künftige IO-Erweiterungen |
| 3 | **`CoachWriteResult`-Typ:** Jetzt definieren oder implizit aus Implementierung ableiten? | Route und Domain koppeln erst im Integrationstest; möglicher `undefined`-Bug im Route-Response |

# Pre-Mortem: Coach-Editor Studio #177

**Datum:** 2026-06-19  
**Plan:** `.cursor/plans/coach-editor_#177.plan.md`  
**Typ:** 1b — Logik, Spec & API-Vertrag  
**Reviewer:** GLM-5.1

Ich habe Plan, Spec (`mpz-studio.md` Z. 196–204), Validator (`validate-coach-messages.mjs`), Typen (`types.ts`), `mpz-station-dialog.ts` als Referenzimplementierung, `coach-triggers.ts`, `mpz-content-io.ts` und eine bestehende Dialog-Route gelesen.

**Wo Plan ∩ Spec ∩ Code tragfähig sind:** `duo ⇔ duo-split`-Constraint, `mascot`/`placement`/`trigger`-Whitelists, `hub-complete`-Eindeutigkeit und `room-first.slug`-Existenz sind in Plan, Spec und Validator **konsistent** spezifiziert. Fehler-Mapping-Grundgerüst (`SCREAMING_SNAKE_CASE`, `{error, message}`) hält sich an die Projekt-Konvention.

---

## Fund 1: HTTP-Status-Mapping — Plan sagt 400, bestehende Studio-Domain-Routen liefern 422

**Was widersprüchlich ist:**  
Plan Z. 149/168–183 ordnet alle Domain-Codes (`DUPLICATE_ID`, `INVALID_TRIGGER`, `INVALID_MASCOT`, …) **HTTP 400** zu — explizit mit Verweis „wie Dialog/Hotspots". `mapDialogError` in Dialog-Route Z. 119 liefert tatsächlich **400** für `DIALOG_CLIENT_ERROR_CODES`. **Aber** die anderen Studio-Domain-Routen (Stammdaten, Hotspots, Medien) mappen Domain-Fehler auf **422**, nicht 400. Es existieren also **zwei verschiedene Status-Mapping-Dialekte** im Codebase, und der Plan wählt den Dialekt, der zur Dialog-Familie gehört — nicht zur Hauptlinie der Stations-CRUD-Routen.

**Warum später teuer:**  
Das Frontend muss für „semantisch gleiche Fehlerklasse" (Domain-Validierung schlägt fehl) zwei Status-Codes handhaben: 400 bei Coach/Dialog, 422 bei Stations-Stammdaten/Hotspots/Medien. Fehler-Handler, Retry-Logik und Test-Assertions werden zweigleisig. Wenn später ein globales Studio-Fehler-UI gebaut wird, muss für Coach eine Ausnahme codiert werden.

**Wann es beißt:**  
Bei Integration des Coach-Panels in das bestehende Studio-Frontend (Issue #170 Epic). Frontend zeigt z. B. „422 → Validierung, roter Kasten" bei Stammdaten, aber „400 → Bad Request, gelber Kasten" bei Coach — wird als Bug gemeldet.

**Billige Gegenmaßnahme jetzt:**  
Ausdrücklich im Plan verankern: „Domain-Fehler-Codes → **422** (wie `stations/[slug]/stammdaten`, Hotspots, Medien), analog `MpzContentIoError.code === 'VALIDATION'`." `COACH_CLIENT_ERROR_CODES` → 422 statt 400. Domain-Codes die nicht Client-Errors sind (`NOT_FOUND`) bleiben 404.

---

## Fund 2: `INVALID_MILESTONE` — Obergrenze nur im postValidate, nicht in der Domain

**Was widersprüchlich ist:**  
Plan Z. 178 (Domain-Tabelle) definiert `INVALID_MILESTONE` nur als *„milestone fehlt, nicht ganzzahlig, oder `< 0`"* — die **Obergrenze** `milestone < stationCount` fehlt. Plan Z. 198 (postValidate-Tabelle) spezifiziert sie korrekt: *„0 ≤ milestone < stationCount"*. Validator Z. 96 prüft beide Seiten. Die Domain prüft (laut Plan) nur die Untergrenze.

**Warum später teuer:**  
Derselbe inhaltliche Fehler („milestone = 99 bei 12 Stationen") kann über **zwei verschiedene Pfade** mit **unterschiedlichen Fehlercodes** landen: Domain durchlassen → postValidate fängt → 422 `VALIDATION` (generische Nachricht). Negativen Wert fängt Domain → 400 `INVALID_MILESTONE` (präzise Nachricht). Frontend, Tests und MPZ-Nutzer sehen für „milestone ungültig" zwei verschiedene Antworten — je nach Vorzeichen.

**Wann es beißt:**  
Bei der ersten Nutzer-Interaktion mit „milestone zu hoch". Domain-Test auf `INVALID_MILESTONE` deckt nur den `< 0`-Pfad ab. MPZ-Redakteur sieht „VALIDATION: Post-Validate fehlgeschlagen" statt „INVALID_MILESTONE: milestone 99 außerhalb 0–11".

**Billige Gegenmaßnahme jetzt:**  
Domain `INVALID_MILESTONE` im Plan um Obergrenze ergänzen: *"`milestone` fehlt, nicht ganzzahlig, `< 0` oder `>= stationCount`"* — Domain muss `stationCount` via `readStations()` holen (wie `findHubStation` in `mpz-station-dialog.ts` Z. 128). Domäne spiegelt dann vollständig den Validator Z. 93–102.

---

## Fund 3: `modes`-Entfernung im PATCH — API-Vertrag ohne Format

**Was widersprüchlich ist:**  
Plan Z. 203 sagt *„Keine Checkboxen gewählt → `modes` im JSON weglassen"*. Das ist eine Serialisierungsregel. **Aber** der PATCH-Input-Typ, der dieses „Weglassen" vom Client signalisiert, ist nicht definiert. Vergleich mit `mpz-station-dialog.ts`: `tail?: DialogBubbleTail | null` (Z. 67) — dort signalisiert `null` die Löschung. Für Coach-Modes wird nicht festgelegt: `modes: null`? `modes: []`? `modes: undefined` (Feld weglassen)? Validator verbietet `modes: []` (Z. 82), ist also keine Option.

**Warum später teuer:**  
Frontend und Backend müssen sich auf exakt eine Semantik einigen, sonst bricht die Integration: Sendet der Client `modes: null`, der Server interpretiert es als „nicht ändern" (`undefined`-Pfad im Patch), bleibt `modes` versehentlich erhalten. Sendet er `modes: []`, schlägt der Validator nach Write zu (leeres Array verboten) — Write-Rollback → 422 für eine eigentlich legitime „modes entfernen"-Aktion.

**Wann es beißt:**  
Bei der ersten „Modus-Einschränkung wieder entfernen"-Aktion im Coach-Formular. Frontend-Entwickler muss raten, testet gegen die eine Semantik, das Backend implementiert die andere → Bug in Integrationstests oder in Produktion.

**Billige Gegenmaßnahme jetzt:**  
Im Plan PATCH-Typ explizit definieren: `modes?: readonly EntryMode[] | null` — `null` = Feld entfernen (Serialisierung lässt `modes` weg), `undefined` = Feld nicht berührt, Array = setzen. In `parsePatch` der Route analog zu `gruppe`/`tail` in Dialog (Z. 38–48) behandeln.

---

## Fund 4: `modes?: readonly EntryMode[]` — irreführender Typ aus Access-Token-Domain

**Was widersprüchlich ist:**  
`types.ts` Z. 181 deklariert `modes?: readonly EntryMode[]`. `EntryMode` ist in `access-tokens.ts` beheimatet — ein **Zugangs-Token-Konzept** („fest"/"heft" als Zugangsmodi für Besucher). Dieselbe Union wird hier für Coach-Anzeigemodus zweitverwendet. Im Editor-Kontext wird die Wiederverwendung „Coach-Modus" genannt, im Runtime-Kontext „Entry-Modus" — gleiche Werte, verschiedene Begriffe.

**Warum später teuer:**  
Sobald ein drittes Feature `EntryMode` für ein anderes Konzept mitnutzt oder sich Access-Token um `gast`-Modus erweitert, „erbt" der Coach automatisch ein neues modes-Label, das er semantisch nicht meint. Ein Rename von `EntryMode` wird nach 2–3 Features ein Breaking Change über alle Imports.

**Wann es beißt:**  
Wenn #170-Epic weitere modus-abhängige Features bringt und `EntryMode` umbenannt oder ergänzt wird. Compiler-Fehler in Coach-Dateien, weil Typ-Referenz „plötzlich" falsch heißt — ohne dass der Coach-Code logisch geändert wurde.

**Billige Gegenmaßnahme jetzt:**  
Coach-eigenen Alias einführen: `export type CoachMode = EntryMode` (oder direkt `'fest' | 'heft'`) in `types.ts` neben `CoachMessage`. `CoachMessage.modes?: readonly CoachMode[]`. Ein Einzeiler, kein Rename nötig, aber semantische Trennung für künftige Lesende und Compiler.

## Positiv-Befund

Das Fehler-Format (`SCREAMING_SNAKE_CASE` + `{error, message}`) und die `duo ⇔ duo-split`-Constraint sind in Plan, Spec und Validator sauber auf einer Linie — kein Konflikt.

| # | Entscheidung | Konsequenz wenn aufgeschoben |
|---|--------------|------------------------------|
| 1 | **HTTP-Status:** 400 (wie Dialog) oder 422 (wie Stammdaten/Hotspots)? | Frontend braucht zwei Fehler-Handler für dieselbe Fehlerklasse |
| 2 | **`INVALID_MILESTONE`-Obergrenze in Domain:** Jetzt ergänzen oder nur in postValidate? | Unterschiedliche Fehlercodes für positiv/negativ out-of-range; unscharfe Fehlermeldung bei zu hohem milestone |
| 3 | **`modes`-Entfernung im PATCH:** `null`, `undefined` oder anderes Signal? | Frontend-Backend-Vertrag unklar; erste „modes entfernen"-Aktion bricht |
